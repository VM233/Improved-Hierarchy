# Hierarchy row presentation lifetime

The frozen MarbleBattlers Unity 6000.6 capture `victory-profile-window.json`, frame 101, records 22.005 ms and 377.8 KB in `NewHierarchyWindowController.RepaintAll`. Its tree has one Hierarchy window, 1,551 visual nodes, 35 rows and depth 18. The controller clears every row presentation on every `hierarchyChanged`, although most bound objects and their presentation inputs have not changed. It then destroys and recreates their generated icons. Unity's separate `HierarchyView.RefreshItems` cost is not attributed to this package.

## Authority and lifecycle

Unity owns window roots, row recycling, the bound `HierarchyViewItem`, its handler and GameObject. The window controller owns one row-discovery list and scheduled callback per attached window. It releases both at root detach. The row renderer owns each attached row's last presented object, name, active state, component sequence, settings revision and display name. It releases that state, generated icons and inline overrides at row detach. A row that binds a scene or becomes unbound clears its previous presentation and never substitutes its old GameObject.

Settings are serialized by `HierarchyColorSettings`. OnValidate and the explicit preferences save publish a presentation revision, covering every setting and preset. Rows compare that revision rather than maintain an incomplete independent settings hash. GameObject name, active state and component identity/order are read from their owners at the existing refresh cadence. An unchanged presentation restores the display label after a native rebind without recreating icons. A changed presentation is rebuilt once. Unity 6000.6 uses its public typed node and handler API, while the supported older engine branch reads the corresponding internal fields and exposes missing reflection contracts instead of suppressing exceptions.

## Static Cost Ledger before executable writes

The frozen acceptance fixture uses one window, 35 disjoint row subtrees, 1,551 visual nodes, depth 18, nine color presets and at most 32 components per displayed GameObject. The current first 2,000 scene objects contain at most 22 components each. The test's explicit 32-component bound is independent of scene population, which is not traversed by this renderer. There is no scene-wide or cross-row component search. Production cost is linear in visible row components, not total scene objects.

One discovery visits 1,551 nodes. One presentation pass performs at most three first-match row searches, 35 component-list queries and 1,120 component reference comparisons. Changed rows perform three icon-cleanup traversals, two icon-host searches and the existing two icon-source component queries. Across the frozen pass the conservative upper bound is nine visual-tree traversals (13,959 node visits), 105 component queries, eight component-list passes (8,960 component slots), and 315 preset comparisons. New icon production remains bounded by the existing ten-icons-per-row setting plus one main icon and one root: at most 420 generated elements. No new scan axis or polling frequency is added.

Steady unchanged passes allocate no component arrays, row states or icons. Cached component capacity is at most 1,120 references plus 32 scratch references, and retained row/window ownership is at most 35 row states and one scheduler. The scratch/cache allowance is 64 KiB, excluding unchanged existing Unity visual elements and GameObject names returned by the native API. Initial population and genuine presentation changes retain the existing icon construction allowance. All operations run synchronously on the Editor main thread. Status: pass for the frozen fixture. Timing and allocation must still be measured after adoption.

Focused tests use at most 35 synthetic rows and 32 components per object, with one test fixture alive at a time. They cover native label rebinding, unrelated hierarchy changes, component additions/removals/reordering, active state, settings changes, name-prefix whitespace, row reuse for a different object and a scene row, and detach cleanup. The allocation comparison warms both code and component-list capacity before measuring unchanged passes. Exact icon identity and ownership, not a copied implementation predicate, establish that rebuilds were avoided. A real hierarchy tree and bounded profiler capture complete integration validation.

## Test cleanup counterexample

The first 1.0.2 test run reported ten passing leaves, but a subsequent scene read found `Camera Object` with Camera, BoxCollider and Rigidbody after the package-test reload. Replaying only the component-reordering test in workflow `e2da7ee1a61a` reproduced the same residual object, ID `18691697755190`, despite its passing assertion result. Unity Test Runner's `PerformUndoTask` runs after test teardown and calls `Undo.RevertAllDownToGroup`. The reorder API records Undo, while the fixture previously destroyed its GameObject without retiring that record. The later Undo recreated the object. Version 1.0.3 gives the synchronous reorder operation its own Undo group and reverts that group before destruction. No user Undo group is reverted by the fixture. This adds one bounded Undo group and one reversal to the existing single reorder test, with no production-code or cost change. Final acceptance must also read the caller scene after the test workflow and verify zero test objects.
